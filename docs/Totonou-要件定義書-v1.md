## 1. コンセプト

**Totonou ＝ 一日を整えるAI秘書**

> メールもタスクも予定も、朝ひらけば、ととのう。

- 受信箱を開くたびに一日が散らかる。Totonouは朝1回開けば、今日やることが全部揃っていて、メールの返信すら下書き済み。あとは片付けるだけ。
- 夜には一日の実績から日報が自動で下書きされ、AIが明日への改善アドバイスをくれる。
- 新しい習慣を作るアプリではなく、**既にある日報習慣から手作業を抜くアプリ**。

### 解決する課題（実体験ベース）

| 現状 | Totonou後 |
|---|---|
| メール・SNSに一日の主導権を奪われる | AIがトリアージし「今日やるべきこと」に変換 |
| 紙の日報に予定・実績・振り返りを毎日手書き | 実績は自動記録、振り返りはAIが8割下書き |
| 所要時間の記録が面倒で改善につながらない | 開始/完了ボタンの副産物として自動計測 |

### 対象ユーザー

- 第一ユーザー: 自分自身（ハッカソン後も毎日使う前提）
- 想定拡張: 複数メールアカウントを持つ個人事業主・フリーランス

## 2. 一日のループ（コアUX）

```
朝  : ブリーフィング …… 予定＋タスクを確認、今日の計画が決まる
日中: 実行 ………………… タスクの開始/完了ボタン → 実績時間が自動記録
夜  : 振り返り …………… AIが日報を下書き、明日への改善提案
```

## 3. 機能要件

### Must（Day 2で完成させる。これだけでデモが成立する）

**M1. 朝のブリーフィング画面（Today Briefing）**
- 冒頭に3秒サマリー「今日は予定3件、要返信2件、タスク4件。午後は空いています」＋元気の出る一言（AI生成）
- 今日の予定リスト（Googleカレンダー由来）
- やることリスト（メール由来タスク＋手動タスクの統合）
- タスクは2軸で分類表示
  - 優先度: 🔴今すぐ / 🟡今日中 / ⚪いつでも
  - 性質: すきまタスク / じっくりタスク
- 1行入力でタスク追加。全タスク完了で「今日は完了です🎉」
- 今日の目標を1行入力できる

**M2. メール取り込み＋AIトリアージ→タスク化**
- Gmail連携で未読・直近メールを取得（取得範囲は設定に従う: 直近100件 / 直近5日分）
- 前処理（機械的除外→AI判定の順でコスト削減）
  0. `category:forums` を私信・コミュニティ候補として最優先で抽出（検証で純度最高と確認）
  1. `category:promotions` / `category:social` をクエリ側で除外
  2. no-reply / noreply / news@ / info@ 系差出人を除外
  3. ドメインのホワイト/ブラックリスト適用
  4. 残りをAIが分類: 要返信 / 要対応 / 情報のみ / 無視
- 要返信・要対応をタスクとしてブリーフィングに自動投入（差出人名・元メールへのリンク付き）
- 宛先ベースでアカウント判定（gmail / goodsystem）しラベル表示

**M3. タスク実行＋実績時間の自動記録**
- タスクごとに開始/完了ボタン。押下時刻から所要時間を自動計算
- メール由来タスクの完了時、元メールをGmail側でも既読化（`modify_email`で確認済み。オン/オフ設定可）
- 未完了タスクは翌日へ持ち越し

**M4. 夜の振り返り画面（日報の自動下書き）**
- 既存の日報フォーマットを出力形式として踏襲:
  - 今日の予定 vs 実際の結果（所要時間）
  - 今日の目標 → 今日の結果（AIが実績から下書き）
  - グッジョブ・感謝 / バッジョブ・反省（AIが下書き→本人が編集）
  - ルール化すること / 改善策（AIアドバイス。例:「メール処理に90分。朝イチ30分に固定しては？」）
  - 励まし・自分へのエール（AIが生成）
- 未完了タスクの持ち越し確認「明日に回しますか？」
- 日報のHTMLエクスポート

### Should（Day 3前半。余裕があれば）

- **S1. 返信ドラフト生成**: メール詳細画面でAIが返信案を生成→編集→承認ボタンで送信（Human-in-the-loop）。送信時は `threadId` のみ指定してスレッド返信（`inReplyTo` は渡さない。検証で確定）
- **S2. 処理履歴ログ**: 「30件処理、要返信3件、タスク5件生成」等のエージェント活動表示。実体は `activity_logs` をcorrelation_idでグルーピングした集計ビュー（VibeLoggerログの再利用であり専用実装は最小）
- **S3. デモ用シードデータ**: リアルな未読メール30件＋1週間分の実績データ投入スクリプト
- **S4. ポモドーロ×声かけ（テキスト版・はっぱがけ秘書）**: タスク開始でポモドーロタイマー起動（25分作業＋5分休憩、見積時間から本数を自動計算）。区切り目（開始/25分経過/休憩終了）にAIが声かけ文を生成し、**画面上のトースト/バナーで表示**（音声読み上げは今回なし・フェーズ2へ）。🔴タスクが未着手のまま放置されたら着手を促す「だらだら検知」。口調はプリセット選択（例: 優しい秘書/熱血コーチ/執事風）。作業中の割り込み声かけはしない（集中を壊さない設計原則）
  - v1.4変更: 音声合成（Aivis Cloud API＋Web Speech APIフォールバック）は**今回実装しない**。`notify()` を抽象化しておき、フェーズ2で `speak()` 実装を差し込める構造にする
- **S5. マルチユーザー化（フェーズ2）**: Supabase AuthのGoogleログインを導入し、開発メンバー2人がそれぞれ自分のGoogleアカウントで利用できるようにする
  - フェーズ1（先行・必須）: 認証なしの単一ユーザー構成でM1〜M4を完成させる。ただし全テーブルに `user_id` カラムを最初から持たせる（後付けのデータ移行を回避）
  - フェーズ2: Supabase AuthのGoogleプロバイダ有効化（Gmail/Calendarスコープ付与）＋全テーブルにRLSポリシー「自分の行のみ読み書き可」＋Google Cloud側テストユーザーにメンバーを追加（審査不要）
  - この構成ではGmailアクセスはMCPではなく、Authで得たトークンによるGmail API直叩きが自然。検証済みの知見（クエリ構文・除外レシピ・threadId返信・既読化）はAPIでもそのまま適用可
  - 着手条件: フェーズ1のM1〜M4が結合済みであること。Devinへ独立タスクとして切り出す

### Could（日曜に余力があれば1つ選ぶ）

- **C1. 日程調整（段階実装）**: メールから日程候補を検知→カレンダー空き確認→予定登録
  - **ライト版（日曜候補・半日以内）**: AIがメール本文から日時を抽出し、タスク詳細画面（画面②）に「カレンダーに登録」ボタンを表示。既存予定と重なる場合は警告のみ。新画面は作らない
  - **フル版（ハッカソン後）**: 空き時間からの候補提案＋返信文生成まで行う日程調整画面（Stitch未着手のまま）
- **C2. Xserver直結チャネル**: goodsystem.jpをIMAP/SMTPで直接送受信（ポーリング式・ボタン押下で更新）。名義問題の根本解決
- **C3. 返信文体の学習**: 送信済みメールから文体を抽出しドラフトに反映
- **C4. 時間軸グリッド表示**: 日報の6時〜23時グリッドを朝画面で再現
- **C5. 週いちの振り返り＋「今週の自分褒め」**: 週1回、AIが1週間分の `daily_reviews` を読み返して振り返りを生成
  - **過去の自分に褒められる**: 週初の目標・日々のエールを引用し、達成した事実と突き合わせて褒める（例:「月曜のあなたが『やりきりたい』と書いた見積もり、金曜に完了しています」）。根拠が自分自身の言葉である点が独自価値
  - **「今週の自分褒め」下書き**: AIが1週間の日報から自分を褒める文章を下書き → 本人が編集（固有名詞・仕事の詳細をここで除去できる） → 「みんなに投稿」ボタン（投稿先のタイムラインはフェーズ3。それまでは自分の記録として保存）
  - 実装は `daily_reviews` の週次集計＋AI生成のみで、新規データ構造は最小（投稿保存用に `praise_posts` を将来追加）
  - デモ可否: シードデータ（S3）に1週間分の実績があるため、日曜に余力があればデモ提示可能

### チャネル抽象（将来拡張の仕込み）

- `MailChannel` インターフェース（`fetchMessages` / `readMessage` / `sendReply`）を定義し、今回はGmail実装のみ差す
- `messages` テーブルに `channel`（今回は gmail 固定）と `account`（gmail / goodsystem）カラムを最初から持たせる
- C2実装時はimapflow＋nodemailerでインターフェースを満たすクラスを追加するだけ

### データモデル（最小）

- 全テーブル共通: `user_id` カラムを最初から持たせる（フェーズ1は固定値、フェーズ2でSupabase Authのユーザーと紐付け＋RLS適用）
- `messages`: messageId(PK) / user_id / channel / account / from / subject / body_text / received_at(UTC) / category / triage_result
- `tasks`: id / source(email|manual|calendar) / message_id(nullable) / title / priority / task_type(sukima|jikkuri) / status / started_at / completed_at / due_date / carried_over_from
- `daily_reviews`: date(PK) / goal / result / good_job / bad_job / rules / improvements / cheer / exported_html
- `activity_logs`: id / ts / level / operation / message / correlation_id / context(jsonb) / human_note / ai_todo → VibeLogger方式。S2の表示とM4の日報材料
- `settings`: dreams（夢・希望）/ monthly_goals（今月やりたい事）→ AIアドバイスの文脈として参照 / fetch_range（メール取得範囲: 100件 or 5日分）/ coach_persona（声かけの口調プリセット・テキスト表示）/ mark_as_read（完了時の既読化オン/オフ）

## 6. Gmail MCP検証結果の反映（2026-08-13実施・計40回のツール呼び出し）

検証レポート（verification.md）で確定した設計判断:

1. **承認UIはアプリ側に置く**。返信案はSupabaseに保存し、承認ボタンで `send_email`。Gmail下書きは読み取りこそ可能（`is:draft` 検索→messageIdで `read_email`）だが、編集・指定送信ができないため採用しない
2. **分類は自前で行いSupabaseに保存**。ラベルは「逆引き（メッセージ→ラベル）」のみ不可で、一覧取得・付与削除・`label:`/`category:` 絞り込みはすべて動作。自前ラベルによる分類状態の管理も可能（採用する場合は `list_email_labels` で名前→IDの対応表を先に引く）
3. **一覧→詳細の2段構え＋キャッシュ必須**。read_emailは重い。取得済みメールはmessageIdキーで保存し二度読みしない。ドメイン足切り→詳細取得の順
4. **HTMLメールは前処理**。タグ・コメント除去後にAIへ渡す（トークン数倍対策）。リンク判定は表示テキストでなくhrefを見る
5. **日時は取得時にUTC正規化**。UTC/JST混在＋アカウントTZ(PDT)の罠あり。期間分割クエリは前後1日オーバーラップ＋messageId重複排除
6. **送信名義は当面Gmail名義**（shimamuraweb3.0@gmail.com）。goodsystem宛への返信時はUIに注記表示。根本解決はC2で
7. 件名の文字列を信頼しすぎない（送信元エンコード起因の文字化け実例あり）。固有名詞抽出は本文と突き合わせ
8. **既定の検索範囲はゴミ箱・迷惑メールを含まない**。網羅性が要る処理では `in:anywhere` を明示。「ヒットしない＝存在しない」と即断しない
9. **私信の第一候補は `category:forums`**。実測で私信・コミュニティメールが集中し純度最高。`category:personal` は残余バケツなので私信と解釈しない

### 追加検証の結果（実装前チェック・完了）

- [x] **返信のスレッド継承 → 成功**。`threadId` のみ指定で元スレッドに繋がる。S1は「スレッド返信」で確定。**`inReplyTo` は使わない**（渡すべきRFC822 Message-IDが取得不能のため）。継承はGmail独自の仕組みなので、非Gmail宛の対外返信を扱う際は受信側での見え方を実機確認する（今回はデモ対象外）
- [x] **`modify_email` での既読化 → 成功**。`UNREAD` の付与/削除が双方向に動作（検証後の復元も確認済み）。Gmail側での既読管理が可能になったため、M3に反映

### 実装前の追加検証（8/15 実施予定・担当: 島村）

- [ ] **Google Calendar 疎通（10分）**: Gmail検証と同じGoogle Cloudプロジェクトで、①今日の予定一覧の取得 → ②テスト予定の登録 → ③削除、の往復を確認。M1（予定表示）とC1ライト版の前提。Calendar APIは有効化済みのはず（Gmail検証時に同時有効化）
- ~~Aivis Cloud API 音声出力~~ → **v1.4で取り消し**（音声読み上げをフェーズ2へ延期したため。フェーズ2着手時に実施）

### 実装中に注意する残課題（verification.md「実装着手前に必ず潰すべきもの」より）

- `after:`/`before:` のTZ基準が未確定（PDT推測）→ 本設計はオーバーラップ＋重複排除で吸収済みだが、全件走査を厳密化する場合は境界検証を行う
- `modify_email` の `labelIds` 引数（上書きの可能性）には触らない。使うのは `addLabelIds` / `removeLabelIds` のみ
- 一括操作（`batch_modify_emails`）・削除系は当面使用しない

## 7. 非機能要件

- **送信は必ず人間の承認を挟む**（誤送信防止。設計原則）
- メール処理対象は設定で選択可能: **直近100件 / 直近5日分**（既定は直近5日分。APIコスト・時間の暴走防止のため、いずれの場合も1回の取り込み上限は100件とする。`maxResults=100` の動作は検証済み）
- ログ出力: **VibeLogger方式の構造化ログ**（operation / context / human_note / ai_todo）を採用。開発時はファイル出力（Claude Code・Devinのデバッグ用）、本番はSupabase `activity_logs` テーブルに記録し、S2の履歴表示・M4の日報材料と共用。本文・氏名・アドレス等の個人情報および秘密情報はログに記録しない。実装規約は別紙「Totonou-ログ実装ガイド.md」に従う
- 秘密情報（APIキー・OAuthトークン）は環境変数管理。リポジトリにコミットしない
- デプロイ済みURLで動作すること（「ローンチ」要件）
- 発表資料・デモでは実在の氏名・メールアドレスをマスクする

## 9. デモシナリオ（3分想定）

1. **課題提示**: 実物の手書き日報を見せる。「毎日これを書いています。手作業を全部AIに渡したのがTotonouです」
2. **朝**: ブリーフィングを開く。メール由来タスクが自動で並んでいる（「自分で入力していないのに今日が揃っている」を強調）
3. **日中**: すきまタスクを開始→完了。実績時間が自動記録される
4. **夜**: 振り返り画面。日報が8割下書き済み。AIの改善提案と「励まし」を見せる
5. **締め**: 全タスク完了画面→「メールもタスクも予定も、朝ひらけば、ととのう。」

補足スライド: MCP検証・計40回の知見（category:personalの罠、category:forumsの発見、TZ問題、既定検索がゴミ箱を除外する罠）＝AIエージェント活用の工夫として提示

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| Gmail連携が当日不調 | シードデータ（S3）でデモ成立させる。検証済みなので発生確率は低 |

| 時間切れ | Must 4つ完成時点で一度デモリハ。以降は追加より磨き込みを優先 |
